## 2026-08-24 Next.js 重启"失败"诊断结论（用户报告：运行时只有一个进程、重新运行失败）
- 用户环境：d:\workspace\知识底座_论文生成\z-vlm-forge\core（Next.js 14.2.15，端口 3000）
- **根因不是扩展 bug**：三次端到端复现（含"编译后强杀再重启"的精确路径）证明 taskkill /T /F 杀 4 层链（cmd→node(npm)→cmd→node(next dev)→node(start-server)）完全干净、端口立即释放
- 真相：Next.js 二次启动打印 "✓ Ready" 需 8~17s+（webpack 缓存恢复 + @code-inspector 动态 import 警告拖慢），期间日志停在 "✓ Starting..."、页面无响应 → 用户误判失败；其 08:44:56 的"失败"实例（PID 14056）实际存活数小时且一直监听 3000（诊断时被清理）
- "就一个进程"：树视图按"监听端口"展示服务，Next.js dev 整链 5 个进程里只有 start-server.js 监听端口 → 只显示 :3000 一个条目，属设计行为；fixtures/app-a 两个端口故显示两条
- taskkill /F 被杀进程退出码为 1，日志"脚本已退出（代码 1）"是正常现象
- Windows 注意：外层 shell 调 powershell 时 $ 会被吞，复杂命令写 .ps1 文件再 -File 执行
- 待办（未实施）：runner.ts 可在启动后检测到实例首个端口监听时追加提示（如"[npm-run] 检测到服务监听 :3000，等待应用 Ready..."）以消除静默窗口期的误判

## 单服务重启对 Next.js 无效的根因 + 闪窗定位（0.5.3 已修复提示）
- 用户实测 fixtures/app-b（自包含 node server.js）单服务重启正常；Next.js dev 不行
- 根因：Next.js dev 的端口监听者 start-server.js 是 **worker 模式脚本**——只在 NEXT_PRIVATE_WORKER=1 且有父进程 IPC（process.send 收 nextWorkerOptions）时工作；扩展按 cmdline 裸拉起后它立即退出、不监听端口；同时 next dev 主进程发现 worker 死了也跟着退出（日志中 [?25h 是其退出时光标恢复序列）
- cmd 闪窗元凶（高频进程快照实证）：next dev 关闭时 spawn 的 node_modules\next\dist\telemetry\detached-flush.js（telemetry 落盘进程，detached 且无 windowsHide → 闪一个控制台）。扩展自身 spawn 均带 windowsHide:true 不闪。用户侧消除法：项目里跑 `npx next telemetry disable`
- 修复（runner.ts）：respawnService 后新增 verifyRespawn——轮询 8s 验证目标端口由新进程子树恢复监听；新进程退出/超时未恢复 → 输出面板+showWarningMessage 提示"该服务可能依赖脚本主进程，请重启整个脚本"
- 版本 0.5.3 已打包安装到 CodeBuddy（npm-run-manager-0.5.3.vsix, 34.88KB）；.tmp-diag 与旧 vsix 已清理
- 用户实测 0.5.3 验证通过：Next.js dev 单服务重启 → 1s 轮询即捕获"新进程已退出"→ 输出准确原因与"请重启整个脚本"指引；日志中间的"启动器进程已结束，剩余服务由扩展代管继续运行"是退出瞬态的标准文案，随后被失败提示纠正，无实际影响
