## v0.5.0 重新设计：单服务独立重启（用户一致性论点胜出）
- 用户论证"既然可单独停止，就该可单独重启"，推翻我此前"整脚本重启"的保守方案
- 实现链路：
  - sysSnapshot 抓 CommandLine（Win: CIM 第 4 列，限次切分防命令行含 |；Unix: ps args=）；解析抽为 parseProcessListWin/Unix 可单测
  - ServiceInfo.cmdline 由 monitor tick 从进程快照回填
  - runner.respawnService(inst, svc)：按 cmdline 在 project.dir spawn(shell:true)，PID 入 inst.adoptedPids，输出喂脚本 channel
  - 归属判定 = collectSubtreePids(rootPid) ∪ 每个代管 PID 的子树（关键：shell:true 时记录的是 shell 包装层 PID，监听者是其子进程，必须并子树而非单 PID——集成测试抓出的真 bug）
  - 清理：stop/stopAll/finish(onExit) 均杀 adoptedPids（killProcessTree 杀整树覆盖 shell 层）
- 命令拆分：service 行 → restartService（仅此服务）；service-root 行与 script 行 → restartScript（整脚本）
- 测试 40/40（新增 5 解析单测 + 1 respawn 集成测试：杀→按 cmdline 拉起→端口回来新 PID→并集归属含 45731+45732→清理无孤儿）
- 已装本机 CodeBuddy 待用户验证：45732 行点 ⟳ 应只重启 server-b，45731 PID 不变

## v0.5.0 关键 bug 修复：脚本退出误杀代管服务（用户实测发现）
- 用户场景：先重启 45731 ✓，再重启 45732 → 两个服务全灭
- 根因链：launcher.js（concurrently 同款语义）靠"等待子进程"存活——两个原始子进程都被替换后 Node 事件循环清空 → launcher 自然退出(码0) → 旧 finish() 无差别清杀 adoptedPids → 全灭
- 修复（"扩展代管"状态机）：
  - finish()：adoptedPids 非空 → 不杀代管、实例保留、instance.adoptedOnly=true、onExit 通知（extension.onExit 见 adoptedPids.size>0 则不删 instances/不 detach monitor）
  - respawn 的 close 回调：最后一个代管进程结束且根已退出 → finalizeIfGone 真正终结实例
  - isRunning 含代管状态；run() 守卫用 isRunning；stop() 杀完代管同步 delete（防 finish 误判）
  - 树显示"扩展代管"描述 + tooltip 说明；runner 新增 eventsMap 供 finalize 通知
- 无孤儿保障不变：stop/stopAll(deactivate) 杀 root+全部代管
- 测试 41/41：新增端到端（双服务替换→根自然退出码0→代管仍监听→清理无孤儿）
- 待用户 Reload 验证：逐个重启两个服务后，脚本行显示"扩展代管"，两端口仍在，停止后全清
- 用户第二次被"脚本已退出（代码 0）"输出误导（实际代管服务全活、行为全对）→ 加衔接输出："启动器进程已结束，剩余服务由扩展代管继续运行"；经验：面向用户的输出措辞要区分"启动器进程"与"服务"
- 用户第三次报告同一现象（第二个服务重启→launcher 退出）→ 确认这是 launcher/concurrently 固有语义（原始子进程全部被替换→无等待对象→自然退出），不可消除；已向用户给出定版心智模型，服务存活由"扩展代管"状态保证
- 顺带修复真竞态：代管状态下整脚本重启（stop→start），stop() 杀完代管后不等 close 事件、主动终结实例（children 空且 adoptedPids 空时同步 delete+onExit），否则 startScript 撞"已在运行中"
